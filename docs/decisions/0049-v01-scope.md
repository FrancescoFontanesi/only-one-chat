# 0049. The scope of v0.1

Status: Accepted.

## Context

[requirements.md](../requirements.md) was written before any code existed, and
until now it still said every requirement was pending. An audit of `main`
(2026-11-24) compared it with the code:

- Most requirements are met.
- A few are met only in part:
  - stepping in during a turn;
  - resuming after a provider switch;
  - quotas used for planning;
  - network approvals.
- Some are not started:
  - failover and the backup leader;
  - parallel workers and worktrees;
  - Antigravity as a worker in the delegation chain.

The backlog now freezes for a first release. What is left is:

- the security boundary (ADR 0050);
- provider robustness (ADR 0051);
- the release steps.

For the requirements outside v0.1, there is no evidence yet from daily use of
which ones matter. Building them first would spend effort on guesses.

## Decision

v0.1 is the single-chat workflow: one leader, one implementer, an optional
reviewer, and nodes on Squad, on the user's subscriptions. Each requirement in
requirements.md carries its status, `v0.1` or `post-v0.1`.

| Requirement                                    | Status    | Why                                                                                                             |
| ---------------------------------------------- | --------- | --------------------------------------------------------------------------------------------------------------- |
| R1 one chat, nested activity                   | v0.1      | Done.                                                                                                           |
| R1 stop, answer questions and approvals        | v0.1      | Done.                                                                                                           |
| R1 a new message while a turn runs             | post-v0.1 | The chat takes one message at a time. Queueing or interrupting needs its own design.                            |
| R2 leader by configuration, models checked     | v0.1      | Done. Commit 0A also checks the settings' model names.                                                          |

## Consequences

- v0.1 is complete when three things are done:
  - ADR 0050 and ADR 0051 are implemented;
  - the release steps pass;
  - every `v0.1` row above holds.
- requirements.md no longer reads as a list of pending work. A `post-v0.1`
  requirement stays as written: its text is the target, and its tag says when.
- No new feature for a `post-v0.1` requirement enters before the release, unless
  an ADR moves it into v0.1.

## Reopening after use

A `post-v0.1` requirement is reopened by a new ADR when use in the field shows
it is needed. Signs that would show it:

- **R8 and R2 backup leader:** a leader's quota ends in the middle of the work,
  more than once a week.
- **R6:** delegations wait on each other in practice, on independent files.
- **R1 messages during a turn:** stopping and resending is a frequent workaround.
- **R5 provider switch:** tasks are canceled only because the provider changed.
- **R7 planning:** a chat starts a task the quota cannot finish.
- **R3/R4 Antigravity as worker:** ADR 0051 closes the ACP gaps, and nodes on
  Antigravity are used for work the implementer then repeats.
